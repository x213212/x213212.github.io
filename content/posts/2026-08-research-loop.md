回測跑出漂亮的曲線很容易，難的是三個月後回答：這條曲線是哪一版資料、哪一版程式碼跑出來的？中間換過幾次參數？

這個問題不解決，研究就會退化成「試到好看為止」。所以我把流程本身寫成一條有閘門的流水線。

## 流程

```text
註冊方法
  → 一個預先凍結的試驗
  → 資料目錄 / PIT / 身分閘門
  → 一份因果實作
  → receipts + 固定報告格式
  → 終局決策
  → 自動產生研究線、時間軸、champion 索引
```

每一步都有拒絕條件，不是流程圖上的裝飾。

**預先凍結** — 試驗的假設、資料範圍、判定標準在跑之前就寫死。跑完才決定看哪個指標，那不是研究，是挑數字。

**PIT（point-in-time）** — 資料只能用當下真正拿得到的版本。財報有發布延遲、指數有成分調整，用今天的資料回測昨天，績效會憑空多出來。

**身分閘門** — 在讀大量資料**之前**先驗策略身分：這份 bundle 的雜湊、依賴鎖定、平台環境是否與宣稱的一致。跑完三小時才發現引用到舊版 helper，那三小時就白費了。

**receipts** — 每個階段留下可驗證的憑據，不是靠 log 事後拼湊。

**終局決策** — 一個試驗只有一次結論，不能「再調一下重跑」。要調就是新試驗、新編號。

## 為什麼是「一次一個」

評估器一次只執行一份已凍結的 brief。這個限制看起來慢，但它讓「這個結果對應哪份設定」永遠是一對一的。並行跑十個變體、事後挑最好的那個，統計上就是在做多重比較而不修正 p 值。

## 資料不進 Git

原始資料、runtime 資料庫、日誌、快取、變更前備份都在版控之外，進版控的是它們的**目錄項目與 manifest**。

理由很實際：11 GB 的工作區裡，光 `experiments/` 就 5 GB。把這些塞進 Git 會讓 clone 變成災難，而且資料本身不需要版本化 —— 需要版本化的是「哪個 manifest 對應哪次試驗」。

## 資料來源

| 來源 | 內容 |
|---|---|
| 期交所逐筆成交 zip | 台指期逐筆，排程搶救下載並校驗 |
| 證交所／櫃買 OpenAPI | 月營收快照 |

所有來源都走同一套資料目錄與 PIT 存取，落地時記錄取得時間與校驗值，回測只能讀到「當時真的拿得到」的版本。

## 部署

研究產物晉升成策略 bundle 之後，才會變成部署資產。

- Bundle 是**不可變的 release**，換版本是換 release，不是就地改檔案
- 每個引擎一個 systemd unit，綁定到特定 release
- 部署前跑 preflight，資料新鮮度、身分、環境隔離不過就不啟動
- 上線後先觀察首輪 K 棒，確認決策與回測同源

所以「現在跑的是哪一版」永遠查得到，不用去比對檔案時間。

實際跑過的狀態，分兩層講清楚：

| 引擎 | 服務 | 真單交易器 |
|---|---|---|
| A（加密貨幣期貨） | 主網訊號，長期運行 | **真單在場**，逐輪回報心跳 |
| C（台指期） | 運行中 | 尚未建置，目前只到訊號與模擬 |
| B、D、E | 已部署過，目前停用或模擬 | 未啟動 |

只有引擎 A 走到真錢下單。其餘停在訊號或模擬層 —— 這條線是刻意的，交易器建置本身要另外過一輪 preflight 與帳務隔離檢查。

## 這條流水線實際解掉的問題

大部分量化專案死在同一批坑上。逐一對應：

| 坑 | 這裡的處理 |
|---|---|
| **未來函數** — 用今天的資料回測昨天 | PIT 資料存取，只給當下真正拿得到的版本 |
| **多重比較** — 跑 50 個變體挑最好的 | 一次一份凍結 brief，終局決策不可重跑 |
| **回測與實盤不一致** | 決策與回測同源：live intent 走同一份實作，逐時鐘留 receipt |
| **「現在跑的是哪一版」** | 不可變 release + 依賴鎖定 + 雜湊身分閘門 |
| **偷接舊研究** — 新策略誤引用舊 helper | 讀資料前先驗 bundle 身分、跨策略 import、helper 來源 |
| **靜默失效** — 服務活著但沒在動 | 心跳秒數與資料缺口是獨立指標，不從服務狀態推導 |
| **TCP 沒斷但沒資料進來** | 流量斷流偵測：連線正常、ingress 為 0 就告警 |

其中最花時間的是**回測與實盤同源**。多數系統的回測和下單是兩份程式碼，跑出來不一樣只能事後猜。這裡的做法是同一份決策實作，回測與 live 只差在資料來源與副作用，每根 K 棒的決策都留憑據可以逐一對帳。

工具與測試合計是核心程式的八倍。這類系統的成本不在演算法，在於證明它沒有偷看未來。

流水線本身持續在用 Claude 與 Codex 迭代 —— 工具鏈、測試與稽核腳本佔了大部分的產出，這也是它們數量遠超核心程式的原因之一。
